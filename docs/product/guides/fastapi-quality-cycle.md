# Цикл качества внешнего FastAPI-визарда

Внешний визард может использовать штатный LLM judge Weblate как владельца проверок и изменений. Визард не получает тексты решений и не изменяет `Unit.target` напрямую.

## Контракт

Один `ProducerRun(kind=judge)` включает оба настроенных места судей. Запускать два независимых run для одной проверки нельзя: это удваивает стоимость и создаёт конкурирующие решения. Перед запуском клиент проверяет `capabilities.judge`, `judge_seats=2`, права `translation.auto` и `unit.review`, доступный MT-движок и отсутствие blockers в estimate.

После терминального run клиент читает `/api/producer/projects/{slug}/decisions/` и `/api/producer/projects/{slug}/quality/issues/`. Эти ответы не содержат source, target, candidate или judge evidence: только идентификаторы, opaque revision, результаты двух seats, категории, хеши вариантов и применимость.

Автоматически применять можно только строку с `applicability=ready`, `candidate_verified=true` и сохранённым `candidate_id`. Bulk apply повторно проверяет revision, права, состояние approval и конфликт обязательной терминологии для каждой строки отдельно. Он возвращает новую revision и `application_id`; только реально применённые строки передаются в `/quality/recheck/`.

Approved, stale, forbidden, неполное evidence и терминологический конфликт не обходятся прямым PATCH. Они остаются без изменения и записываются внешним оркестратором как исключения. Ошибка одной строки не должна отменять успешные изменения других строк.

## Повторы и глоссарий

`repeat-drift` группирует одинаковый source и plural form в выбранном языке. В ответе видны только unit IDs и хеши вариантов. Несколько конфликтующих approved-вариантов делают группу непригодной для автоматического ремонта.

Глоссарная проблема возвращается как `hard` для обязательного точного термина или как `advisory` для допустимого словоизменения. Hard-конфликт блокирует bulk apply кандидата. Само обнаружение неодинаковости не разрешает выбрать произвольный существующий вариант: изменение возможно только через кандидата, который проверили оба места судей.

## Отказоустойчивость клиента

GET можно повторять после timeout, HTTP 429 и 5xx с ограниченным backoff. Изменяющий POST нельзя повторять после неизвестного результата: сначала нужно наблюдать сохранённый remote run или завершить строку как транспортное исключение. Конфигурационные ошибки остаются в состоянии ожидания. После ограниченного числа временных сбоев проект завершается с исключениями и доступным экспортом, а не как общий crash.

Функция выключена во внешнем визарде по умолчанию. Включение и проверка на тестовом проекте выполняются отдельно от установки и не являются частью pull request.
